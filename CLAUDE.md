# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository overview

This repo is a personal D&D 5e campaign notebook: hand-maintained Markdown documenting characters, dungeons, and homebrew guides, plus one small self-hosted web app (`sheet-app/`) that renders and live-edits a character sheet during actual play. There is no `statling` package anymore: it was a Python package that lived here and has since been removed (see git history if you need the old implementation for reference).

`statling`'s actual intent was to read a character's YAML data and feed it through a Jinja2 template into an HTML/CSS layout that visually reproduced the real D&D character sheet. What was actually built before it was scrapped only got partway there: a Jinja2 template (`character_sheet_5e_2014.j2`) that rendered the YAML to Markdown, not HTML/CSS, a first step toward the visual-sheet goal, not the goal itself. The per-character `.yaml` data files under `characters/` were removed along with `statling` at the time since nothing consumed them anymore; the human-readable `.md` sheets stayed hand-maintained (including hand-formatting them to resemble the official sheet's layout).

That deferred idea has since been built, in a different shape than originally planned: `sheet-app/` is a Flask app that reads per-character **YAML** files (not JSON, the original plan's assumption, changed when the app was actually built) and dynamically renders an HTML character sheet from them, styled after `characters/2014_marigold_kettlewick.html` (the original one-off hand-built visual reference, still kept for that reason, see Structure below). It's a real, self-hosted, Docker-run app now, not a deferred idea. See `sheet-app/` in Structure below for what it does and how to run it.

## Structure

- `characters/` — character sheets and related reference material, hand-maintained Markdown/HTML.
  - Elowen has two `.md` drafts under different rule editions: `2014_elowen_turnerleaf.md` (2014 PHB rules) and `2024_elowen_turnerleaf.md` (an earlier draft built under the 2024 rules revision). Neither is wired into `sheet-app/` yet.
  - Marigold Kettlewick has several files, each with a distinct purpose:
    - `2014_marigold_kettlewick.md` is her full working sheet, including verification caveats, worldbuilding placeholders, and future-advancement notes.
    - `2014_marigold_kettlewick_clean.md` is the same sheet with all of that open-question/planning content stripped out, just settled stats and backstory. Was built for exporting her elsewhere (e.g. hand-entering into a third-party tool); not auto-synced with the `.md` above if she changes.
    - `2014_marigold_kettlewick.html` is the original one-off, hand-built HTML/CSS page styled to resemble the official WotC sheet layout, meant to be opened in a browser and printed/exported to PDF. This is also the visual template `sheet-app/templates/character_sheet.html` was derived from.
    - `2014_marigold_kettlewick_howto.html` is a standalone "how to play her" quick-reference (tactics, cannon modes, spell usage, survival tips), styled to match her sheet. A copy of it is manually placed at `sheet-app/static/howto.html` for quick access during sessions (see below); the two are **not** auto-synced, re-copy by hand after editing one.
  - There's no import path into tools like D&D Beyond, and no generator for the HTML sheets beyond `sheet-app/` itself; a from-scratch character without YAML data in `sheet-app/data/` needs its HTML sheet hand-built the same way Marigold's was.
- `dungeon/` — session/dungeon-crawl prep notes: `dungeon.md` (room-by-room crawl writeup), `monsters.md` (original 5e-compatible stat blocks for that crawl), `mtg_cards.md` (system for converting Magic: The Gathering booster-pack cards into D&D effects by color identity, used to improvise loot/encounters), `temp.md` (a specific scripted encounter, e.g. the night hag dream sequence).
- `guides/` — standalone homebrew rules guides, e.g. `tarot_based_characters.md` (using tarot spreads/archetypes to drive backstory, personality, and stat generation during character creation).
- `sheet_app_roadmap.md` — running list of future enhancement ideas for `sheet-app/`, written from an actual-play perspective (rest handling, condition tracking, DM tools, etc.), not a commitment or schedule.
- `sheet-app/` — the Flask/Docker character sheet app. See below.

### `sheet-app/`

A small self-hosted web app, actively used to run live character sheets during sessions (currently just Marigold Kettlewick).

- **Data model**: `data/<id>.yaml` is the static character definition (class, stats, backstory, features, inventory) and is the source of truth for a character's build; edit it by hand to reflect an actual character change (leveling up, new gear, etc.). `state/<id>.yaml` (gitignored) holds only the fields that change *during* a session, current/temp HP, hit dice used, death saves, inspiration, XP, currency, spell slots used, kept separate specifically so a live in-session edit can never corrupt the character's actual build. If no state file exists yet, sensible defaults are derived from the character data (e.g. current HP defaults to max).
- **Rendering**: `app.py` (Flask + Gunicorn) merges a character's static data and live state, then renders `templates/character_sheet.html`, a Jinja2-ified version of `characters/2014_marigold_kettlewick.html`. `templates/index.html` lists all characters found in `data/`.
- **Editing during play**: the character sheet page has a "Save Changes" button that POSTs the mutable fields back to the server, which persists them to that character's `state/<id>.yaml`. No JavaScript is used anywhere in the app.
- **Running it**: `cd sheet-app && docker compose -f docker-compose.dev.yml up -d` (first run, builds automatically), then open `http://localhost:8890`. After changing `app.py`, templates, or `requirements.txt`, you must force a rebuild: `docker compose -f docker-compose.dev.yml up -d --build` (plain `up` reuses the cached image and won't pick up code changes). Changes to `data/` or `state/` take effect immediately on page refresh, no rebuild needed, both are bind-mounted, not baked into the image. For faster template/CSS iteration without a rebuild, run `python app.py` directly (needs `pip install -r requirements.txt` in a venv first) and hit `http://localhost:5000`; set `FLASK_DEBUG=1` for auto-reload. Production always runs through Gunicorn (`gunicorn.conf.py`, invoked by the Dockerfile's `CMD`), never `app.py` directly.
- **Published image / CI**: two GitHub Actions workflows automate this. `.github/workflows/release.yml` is a manual `workflow_dispatch` you run with a patch/minor/major choice; it computes the next `vX.Y.Z` tag from existing git tags, pushes it, and triggers `.github/workflows/sheet-app-image.yml`, which builds `sheet-app/Dockerfile` and publishes it to `ghcr.io/mxhdg/dandd/sheet-app` tagged `latest`, `sha-<shortsha>`, and the version tag, then signs it with cosign (keyless, via GitHub OIDC) and runs a non-blocking Trivy scan. `sheet-app/docker-compose.dev.yml` (labeled `sheet-app-dev`) has no `image:` field, only `build:`, so it always builds locally and never pulls the published image; that keeps local dev (`docker compose -f docker-compose.dev.yml up -d --build`) from silently drifting onto a registry build. `sheet-app/docker-compose.prod.yml` is the counterpart for consuming the published image: its `image:` field points at `ghcr.io/mxhdg/dandd/sheet-app:${SHEET_APP_TAG:-latest}`, using standard `/opt/sheet-app/...` bind-mount paths; set `SHEET_APP_TAG` to a specific `sha-<shortsha>` or version tag to pin to that build.
- **Security posture**: runs as a non-root container user (UID/GID 1000 by default, matching a typical single-user Linux host; override via `--build-arg APP_UID=$(id -u) --build-arg APP_GID=$(id -g)` if that doesn't match), read-only root filesystem with `/tmp` as the only writable tmpfs besides the two bind mounts, dropped Linux capabilities, a strict CSP and other security headers, character-id input validated against an allowlist regex to block path traversal, and a capped request body size. There is deliberately **no authentication/authorization or CSRF protection yet**; that's an intentionally deferred gap (see `sheet_app_roadmap.md`), acceptable for a home-LAN, single-table use case but worth revisiting before running this anywhere less trusted.
- **Mobile**: the sheet is responsive down to an iPhone-14-Pro-sized viewport (390px CSS width), verified with headless-Chromium screenshots, not just by inspecting the CSS. If you touch layout CSS, re-verify on a narrow viewport rather than assuming a desktop check covers it.

When editing content in this repo, match the existing Markdown conventions of the file you're in (e.g. the ASCII-art stat blocks in character sheets, the heading/section structure in dungeon prep docs) rather than introducing a new format. For `sheet-app/`, match the existing Flask/Jinja2 patterns already there rather than introducing new frameworks or a JS build step.
